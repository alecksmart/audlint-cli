- (direction) Headless express mode selected because the invocation supplied a complete source artifact in a non-interactive tool context.
- (decision) The spec slug is product-roadmap, derived from the source filename and its consolidated product-roadmap title.
- (decision) The contract covers the full Audlint roadmap as a program-level direction and sequencing spec, not a bounded implementation slice.
- (decision) The source roadmap remains an adopted companion because its item states, priorities, dependencies, detailed scopes, extension protocol, and evidence ledger are load-bearing downstream.
- (decision) docs/architecture/OVERVIEW.md remains an adopted companion because it defines the current implementation and cross-component contracts that all roadmap work must preserve.
- (decision) The force behind the roadmap is to mature the shipped local CLI/TUI in safety, evidence, correctness, performance, and operability before considering a remote product surface.
- (capability) CAP-1 maps R0: establish a dated reproducible quality and release baseline whose local gate passes and whose supported distro checks pass or have explicitly accepted blockers.
- (capability) CAP-2 maps R1: make mutation, dry-run, backup, atomicity, cleanup, and recovery semantics truthful, documented in a checked-in mutation matrix, and enforced for the highest-risk contracts by fixture tests.
- (capability) CAP-3 maps R2: automate the portable quality gate so clean changes receive the same essential local and automated verdict, with documented environment-specific exceptions.
- (capability) CAP-4 maps R3: create a versioned analyzer corpus and reproducible accuracy/runtime baseline that protects the approved corpus, distinguishes trusted from weak labels, and exposes cache and fallback costs.
- (capability) CAP-5 maps R3A: make analyzer execution and cache reuse explicit and proportionate while preserving trusted decisions and meeting a bounded performance envelope across consumers.
- (capability) CAP-6 maps R4: converge consumers on the structured analyzer decision contract, with contract tests for every decision class and fallback reason and no policy reconstructed from display strings.
- (capability) CAP-7 maps R5: refine analyzer decisions only from named evidence, preserving or improving trusted-corpus accuracy with regression coverage and an agreed runtime envelope.
- (capability) CAP-8 maps R6: parallelize non-destructive per-track analysis with bounded resources, deterministic reduction and output, clean cancellation, and serial-equivalent results.
- (capability) CAP-9 maps R7: unify bounded preparation and encoding workers so conversions are serial-equivalent, failures leave no partial replacement, and reruns remain recoverable and idempotent.
- (capability) CAP-10 maps R8: provide selectable or detected dark, light, and no-color terminal themes that remain readable and behaviorally identical across shared UI consumers.
- (capability) CAP-11 maps R9: make workflow readiness, state ownership, failures, next actions, and supported recovery understandable without private planning material.
- (capability) CAP-12 maps G0: decide whether a self-hosted service should exist through an approved product brief, PRD, threat model, and architecture decision that preserve CLI safety and data contracts.
- (capability) CAP-13 maps G1 through G8: if and only if G0 approves the service, deliver it through the preserved conditional dependency sequence with each entry gate satisfied.
- (constraint) Development remains ad hoc and pull-based: roadmap priorities express logical urgency rather than dates, sprints, velocity, or time-box commitments.
- (constraint) A roadmap item advances independently through the defined state model, keeps its stable roadmap ID, and moves to the completion ledger with code, test, or decision evidence when done.
- (constraint) Only one bounded roadmap item is promoted into a build spec at a time unless the user explicitly authorizes parallel work.
- (constraint) Audio files and embedded tags remain authoritative for media content; SQLite holds derived analysis and operator-managed state and is not assumed fully reconstructible.
- (constraint) Destructive audio, tag, artwork, deletion, sync, backup, and database workflows require explicit operator control, truthful dry-run behavior, failure cleanup, and recoverability.
- (constraint) Automated verification uses temporary fixtures; only the explicitly approved /Volumes/Music/Tests corpus may be used read-only through staging that prevents generated files from entering it.
- (constraint) audlint-analyze remains the single recode-decision authority; callers may add safety and presentation but may not recreate analyzer policy.
- (constraint) Shared policy belongs in lib/sh or lib/py, bin entry scripts remain orchestration, and canonical normalized profiles remain SR_HZ/BITS.
- (constraint) Bash 5 and macOS/Linux portability remain mandatory.
- (constraint) Performance work may not weaken deterministic output, failure atomicity, no-upscale behavior, lossy-source guardrails, or trusted-corpus decisions.
- (constraint) The Go/React service direction remains parked until G0 is approved; archived service technology, database, cloud, monetization, and market choices remain hypotheses.
- (decision) Non-goals are automatic release publication, sprint planning metadata, treating roadmap claims as implemented behavior, reopening verified completed work without evidence, and implementing the service before G0.
- (note) Wrapper-only content: source frontmatter dates, status labels, prose transitions, and Next BMAD artifact labels were not duplicated in the kernel; actionable item detail and provenance remain preserved in the roadmap companion.
- (note) The source register references archived runbook and private planning evidence, but repository policy forbids reading or restoring runbooks; preservation is achieved by retaining the roadmap itself as the adopted companion.
- (question) What numeric performance envelopes should the bounded specs for CAP-5, CAP-7, CAP-8, and CAP-9 enforce? The roadmap requires agreed envelopes but does not supply thresholds.
- (question) Which mutation classes must require paranoia backup, and what transaction-consistency guarantee must SQLite backups provide? CAP-2 requires these decisions but the roadmap leaves them open.
- (question) Should G0 ever be promoted from parked, and if so must the service be read-only, write-capable, or permission-tiered? No implementation may infer the answer.
