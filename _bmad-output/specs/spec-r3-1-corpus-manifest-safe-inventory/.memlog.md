- (direction) Headless express mode selected because the user supplied a bounded child slice, the parent contract, explicit exclusions, and a requested artifact path outcome.
- (decision) The child slug is r3-1-corpus-manifest-safe-inventory and the artifact is a standalone R3.1 contract for a later fresh-context bmad-build.
- (direction) The existing R3 SPEC.md and its corpus-manifest.md, brownfield.md, and architecture companion are authoritative; R3.1 narrows their inventory requirements without redesigning or broadening them.
- (decision) R3.1 establishes a trustworthy versioned manifest and read-only objective inventory before any analyzer or benchmark command is allowed to run.
- (capability) CAP-1 Strict manifest contract: maintainers can validate one schema-version-1 corpus-manifest.json with stable corpus and case identities, ordered entries, complete expected values, provenance, trust, files, and checksums.
- (capability) CAP-2 Safe root-relative identity: maintainers can reject absolute, non-normalized, traversal, missing, duplicate, or root-escaping case and file paths while keeping the manifest independent of machine-specific corpus roots.
- (capability) CAP-3 Read-only objective inventory: maintainers can inventory files, SHA-256 values, byte sizes, and applicable media probe facts from an explicitly supplied corpus root while writing only the canonical BMAD output manifest.
- (capability) CAP-4 Human-owned expectations and lineage: maintainers retain explicit control of trusted or weak labels, expected analyzer truth, provenance, and required synthetic lineage, with automation unable to infer or promote them from current Audlint results.
- (decision) The only supported top-level schema_version in this slice is integer 1; corpus_id, immutable corpus_revision, RFC 3339 generated_at_utc, and ordered entries are required.
- (decision) Every entry requires a unique stable id, safe album_path, category real, fake, or edge_case, stable case_class, a non-empty ordered files inventory, expected_source_profile, expected_target_profile, expected_decision, boolean expected_fake_upscale, exact trust, and provenance; expected_analysis_mode is optional.
- (decision) Every file item requires a safe root-relative path, role, lowercase SHA-256 digest, and nonnegative byte count; audio files also carry objective container, codec, sample rate, applicable bit depth, channels, and duration facts.
- (decision) PCM expected profiles use canonical SR_HZ/BITS; DSD-family source expectations use an explicit family label while native probe facts remain on file items.
- (decision) Manifest and file arrays preserve deterministic order; duplicate corpus IDs, entry IDs, and conflicting or duplicate file identities are validation errors rather than silently normalized input.
- (constraint) All stored paths are POSIX-style, relative to the supplied corpus root, normalized without empty, dot, or parent segments, and must resolve inside that root; absolute paths and symlink-mediated escapes are rejected.
- (decision) Trust accepts only the literal values trusted and weak; missing or malformed values fail validation and are never normalized or silently downgraded.
- (decision) Provenance must record its basis, a source reference or recipe lineage, rationale, named reviewer, and UTC review date.
- (decision) A trusted entry is valid only when independent source or synthetic lineage, named human review of all expected values, and checksum-pinned inputs are present; missing trusted truth fails rather than being invented or downgraded.
- (decision) Synthetic derivatives require generation_recipe metadata naming the trusted source checksum, exact audlint-dataset.sh invocation parameters, and relevant encoder or tool versions; independently sourced media omit generation_recipe.
- (constraint) Inventory may enumerate inputs, hash regular files, and collect objective media metadata only; it may not run Audlint analysis or copy current Audlint output into expected values, provenance, or trust.
- (constraint) The corpus root is explicit runtime input and remains immutable: inventory never creates, removes, renames, rewrites, retags, chmods, or deliberately changes timestamps within it.
- (decision) The generated manifest path is _bmad-output/benchmarks/r3-analyzer-corpus-benchmark-baseline/corpus-manifest.json and no output is written under the corpus root.
- (decision) Generated JSON is one UTF-8 object with two-space indentation, lexicographically sorted object keys, LF endings, one final newline, and preserved deterministic array order so its exact SHA-256 is stable contract identity.
- (constraint) CLI entry scripts remain thin; manifest validation and inventory belong in the existing shared Python corpus implementation or a focused shared Python module, using existing shared media-probing policy rather than duplicating it in bin.
- (constraint) Bash 5, macOS and Linux portability, and canonical SR_HZ/BITS normalization remain mandatory.
- (constraint) Automated verification uses repository-owned temporary fixtures only and never touches /Volumes/Music/Tests, a real music library, a live SQLite database, a mounted sync destination, or a destructive media workflow.
- (decision) Focused tests cover valid schema and canonical output, unsupported schema version, stable-ID uniqueness, absolute and traversal paths, symlink-mediated root escape, malformed trust, incomplete trusted provenance or expectations, file inventory and checksum mismatch, synthetic lineage requirements, and read-only inventory behavior.
- (decision) Likely implementation files are bin/audlint-analyze-corpus.sh, lib/py/audlint_analyze_corpus.py or a focused new lib/py manifest module, test/test_audlint_analyze_corpus_smoke.py or a focused new manifest test module, and conditionally the generated corpus-manifest.json when an operator later supplies and approves the real corpus root.
- (decision) R3.1 excludes analyzer corpus execution, staging for analyzers or converters, accuracy verdict execution, cold or warm benchmarking, work/decode/probe instrumentation, performance optimization, and all R3A, R4, R5, and R6 work.
- (note) Wrapper-only content: parent runtime benchmark protocol details, analyzer verdict semantics, converter safety gates, staging snapshots, timing, counters, and later-roadmap work are excluded because they do not change an R3.1 implementation decision.
- (decision) No open product question blocks R3.1; exact CLI flag spelling and internal module split may follow repository conventions as implementation choices without changing the contract.
- (decision) R3.1 coverage validation reports missing required classes across genuine PCM, lossy-lineage fake upscales, sparse genuine high resolution, edge cases, DSD family, large CUE/WavPack, and misleading spectrogram evidence without fabricating cases or labels.
- (decision) Required genuine PCM coverage includes 44.1/16, 44.1/24, 48/24, 96/24, and 192/24; fake coverage spans MP3, AAC, and Opus lineage at multiple source bitrates and 48, 96, and 192 kHz fake target families.
